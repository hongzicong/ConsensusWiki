# Exploiting Commutativity For Practical Fast Replication

## One-sentence summary
CURP separates unordered durability from ordered replication so commutative operations can complete in 1 RTT while preserving linearizability after primary crashes.

## Why this paper matters
The paper shows that a primary-backup system need not wait for ordered backup replication before replying: clients can make requests durable by recording them on temporary [[witness]] storage, while the master executes speculatively and later syncs ordered state to backups.

CURP is important for [[fast-path]] design because its fast evidence is not a Paxos quorum certificate. It is a commutativity-preserving durability record that can be replayed safely in any order after recovery.

## System model
CURP targets existing primary-backup replicated storage systems. The base system has one master and `f` backups, for `f + 1` replicas total, and CURP adds `f` witnesses. Witnesses may fail independently and may be co-hosted with backups, but the paper assumes separate witnesses for applicability to existing systems.

## Fault model
CURP assumes fail-stop failures and explicitly does not handle Byzantine faults. It remains immediately recoverable despite up to `f` failures, and the paper states that it remains strongly consistent even if all replicas fail, although availability may be lost until enough data is recovered.

## Timing assumptions
Safety is not timing-based. The network may be asynchronous and unreliable: messages can be delayed or dropped. The 1 RTT claim is a normal-case latency claim when the master replies and all `f` witnesses accept the client record.

## Main idea
Traditional primary-backup replication entangles ordering and durability: the master orders and syncs updates to backups before replying, costing 2 RTTs. CURP splits the roles:
- backups store ordered durable state,
- witnesses temporarily store unordered request records,
- commutativity makes replay order irrelevant for unsynced requests.

## Protocol roles
- **Client:** sends update RPCs to the master and concurrently records the request at witnesses.
- **Master:** serializes and executes update RPCs, speculatively replies before backup sync when safe, and later syncs ordered state/log entries to backups.
- **Backup:** stores the ordered replicated state or operation log used for ordinary primary-backup recovery.
- **Witness:** stores temporary unordered request records in non-volatile memory, rejects non-commuting records, garbage-collects records after backup sync, and provides records during recovery.
- **Configuration manager / cluster coordinator:** supplies current master and witness configuration; witness configuration is versioned.

## Message types
- `record`: client to witness; asks the witness to durably store an update request.
- `sync`: client to master; asks the master to wait until the operation is replicated to backups.
- `gc`: master to witness; drops saved requests that are now durable in backups.
- `getRecoveryData`: recovery path request to a selected witness for saved requests.
- `start`: coordinator to witness for master/witness lifecycle.

## Local state
- Master keeps the ordered state/log plus the set of currently unsynced speculative operations.
- Witness keeps request records for a particular master until garbage-collected or used for recovery.
- Clients include request identifiers for exactly-once semantics and include `WitnessListVersion` on update requests.
- The system relies on RIFL-style unique RPC IDs and durable result records to suppress duplicates.

## Normal path
The client sends the update to the master and records the same request at all `f` witnesses in parallel. The master executes the request if it commutes with all unsynced operations, returns the result, and asynchronously syncs the ordered outcome to backups.

## Fast path
An update completes in 1 RTT when:
- the master executes and returns a result,
- all `f` witnesses accept the `record`,
- the operation commutes with every witness's saved requests,
- the master sees the operation as commutative with all currently unsynced operations.

The client can then externalize the result without waiting for backup replication.

## Slow path
If any witness rejects or fails to accept the record, or if the master detects a non-commuting unsynced operation, the client cannot complete on the witness path. The client sends a `sync` RPC or uses a master response marked as synced; completion then waits for backup replication, usually 2 RTTs and up to 3 RTTs in the worst case described by the paper.

## Recovery path
Recovery from a master crash has two phases:
1. restore state from one backup using the underlying primary-backup mechanism,
2. select one available witness, stop it from accepting new records, retrieve all saved requests, and replay those requests.

Only one witness is used for replay, not a union across witnesses. This is safe because every request completed on the fast path was recorded in all `f` witnesses, and each witness independently stores only mutually commutative requests. Duplicate replay is filtered by exactly-once/RIFL semantics.

## Commit rule
A client-completed update is safe when either:
- it has been recorded by all `f` witnesses and the master returned the speculative result, or
- it has been replicated to the `f` backups through the normal sync path.

The paper's proof restates this as Rule 1: a client only completes an update if it is recorded in all `f` witnesses or replicated to `f` backups.

## Quorum system
For primary-backup CURP:
- total replicas: `f + 1` primary-backup replicas = one master plus `f` backups,
- witnesses: `f`,
- fast witness requirement: all `f` witnesses accept,
- classic/backup sync requirement: replication to `f` backups,
- recovery witness requirement: one available selected witness after restoring from one backup,
- leader inclusion: the master is on the execution path but witnesses supply unordered durability,
- quorum shape: fixed all-witness fast durability plus one-witness replay, not a majority quorum.

The appendix also sketches a CURP extension for strong-leader consensus protocols with `2f + 1` replicas/witnesses: 1 RTT completion needs a superquorum of `f + ceil(f/2) + 1` witnesses, while recovery collects from at least `f + 1` witnesses and replays requests appearing in at least `ceil(f/2) + 1` witnesses.

## Conflict handling
CURP uses operation commutativity, checked from operation parameters. A witness accepts a new record only if it commutes with every operation currently saved at that witness. The master also syncs before responding if a new operation does not commute with existing unsynced operations.

The paper explicitly excludes state-dependent commutativity checks from witness use; SQL updates whose commutativity depends on current data are an example limitation.

## Safety argument
The informal proof establishes durability, consistency, and linearizability after master crashes:
- completed operations survive because recovery uses one backup plus one witness, and a completed operation is in at least one of them,
- a synced operation is recovered from backup and duplicate witness replay is ignored,
- an unsynced completed operation appears in every witness, so it appears in the selected recovery witness,
- replay order cannot change results because selected-witness records are mutually commutative,
- dependent non-commuting observations force the master to sync before responding.

## Liveness argument
Progress is conditional on the underlying primary-backup system and availability of enough components. If the witness fast path is unavailable because of failures or conflicts, clients fall back to the sync path. During recovery, if none of the `f` witnesses is reachable, the new master waits.

## Key proof ideas
- Separate ordered backup recovery from unordered witness replay.
- Replay from exactly one witness to preserve that witness's pairwise-commutative set.
- Use exactly-once request IDs to make replay idempotent at the RPC level.
- Force non-commuting observations through backup sync so a later recovery cannot erase a visible dependency.

## Important formulas
- Primary-backup deployment: `f + 1` replicas = one master plus `f` backups.
- Witness count: `f`.
- Fast path: accepted by all `f` witnesses.
- Client completion rule: recorded in all `f` witnesses or replicated to `f` backups.
- Consensus extension: `2f + 1` replicas/witnesses; fast witness superquorum `f + ceil(f/2) + 1`; recovery quorum `f + 1`; replay threshold `ceil(f/2) + 1`.

## Relationship to other protocols
CURP is related to [[FastPaxos]] and Generalized Paxos because it exploits commutativity for low latency, but the paper emphasizes that those protocols still need 1.5 RTT end-to-end for clients to receive execution results. CURP is also compared with [[EPaxos]], which uses commutativity for multi-leader consensus, while CURP keeps a strong master and avoids writing reads through consensus.

## Limitations
- Witnesses must determine commutativity from request parameters, not from executing against state.
- Non-commutative operations fall back to the sync path.
- Duplicate suppression via exactly-once semantics is required.
- Witness memory pressure and skewed hot keys can increase rejections.
- Primary-backup CURP focuses on storage systems; the consensus extension is sketched rather than the main implemented protocol.
